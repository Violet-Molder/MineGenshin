1. 问题的起点：渲染文档里的一行代码

在 渲染文档 §1.5 里有这样一段代码：

// 提交时拿到的位姿 → 世界坐标（在渲染回调里）
Matrix4f bonePose = new Matrix4f(info.poseStack().last().pose());
Vector3f local = bonePose.getTranslation(new Vector3f());   // 相机空间平移
Vec3 worldPos = new Vec3(camera.x + local.x, camera.y + local.y, camera.z + local.z);

这里引出了三个问题：

  • 为什么 poseStack.last().pose() 是一个 4×4 矩阵？
  • getTranslation() 从矩阵的哪里取出了平移量？
  • 为什么提取出来的平移量是"相机空间"的，要加上 camera 才是世界坐标？

要回答这些问题，必须先理解一件事：图形学里的 4×4 矩阵到底存了什么。

一句话前置结论：
4×4 矩阵的 左上 3×3 存的是三个基向量（编码旋转+缩放），第 4 列存的是平移量。 最后一行永远是 [0,0,0,1]。矩阵的"列"而不是"行"决定了几何意义。

2. 4×4 矩阵的结构：三根轴 + 一个位置

一个 4×4 变换矩阵（Matrix4f）在内存中是列主序存储的。写成数学形式：

列 0 = X 轴   列 1 = Y 轴   列 2 = Z 轴   列 3 = 平移
0.71 0.00 0.71 2.0 ← 第 0 行
0.00 1.00 0.00 3.5 ← 第 1 行
-0.71 0.00 0.71 -1.0 ← 第 2 行
0 0 0 1 ← 第 3 行（固定 [0,0,0,1]）

第 0 列 = X 轴

新 X 轴在原始 X/Y/Z 三个方向上的分量。这是一个 3D 向量 (m00, m10, m20)。

第 1 列 = Y 轴

新 Y 轴在原始 X/Y/Z 三个方向上的分量。向量 (m01, m11, m21)。

第 2 列 = Z 轴

新 Z 轴在原始 X/Y/Z 三个方向上的分量。向量 (m02, m12, m22)。

第 3 列 = 平移

整个坐标系的新原点位置。向量 (m03, m13, m23)，JOML 里用 getTranslation() 提取。

所以 bonePose.getTranslation(new Vector3f()) 做的其实就是：从 4×4 矩阵的第 4 列 (m03, m13, m23) 取出这三个值，放到一个 Vector3f 里返回。仅此而已——没有计算，就是直接读内存。

关键认识：矩阵的每一列是一个 4D 向量，但第 4 行（除了第 4 列最后一格是 1）全是 0。 所以前三个分量的几何意义分别是 X 轴、Y 轴、Z 轴、平移。这就是为什么叫"4×4 仿射变换矩阵"。

4. 为什么每根轴需要三个数字？

这是很多人最困惑的点——"X 轴不就只管 X 方向吗？为什么需要三个数字来描述它？"

核心答案：因为旋转之后，X 轴不再只指向 X 方向了。

在三维空间里，一根轴本身就是一个 3D 向量，有三个分量 (x, y, z)：

  • x 分量："这根轴往原始 X 方向走了多少"
  • y 分量："这根轴往原始 Y 方向走了多少"
  • z 分量："这根轴往原始 Z 方向走了多少"

用白板笔来类比：

🔄 旋转前

笔尖指向正右方：

X 轴 = (1.00, 0.00, 0.00)
  ↑      ↑      ↑
向右  不上  不向前

看起来只有一个分量非零——因为正好和原来的 X 轴重合。

🔄 绕 Y 轴旋转 45° 后

笔尖指向右前方：

X 轴 = (0.71, 0.00, 0.71)
  ↑      ↑      ↑
向右  不上  向前

三个分量全用上了！这就是常态——只有单位矩阵才看起来只用了一个分量。

所以不是"每个轴需要三个数字"，而是"每个轴本身就是一个三维向量"。 3 个轴 × 每个轴 3 个分量 = 9 个数字 = 3×3 矩阵。

用矩阵乘法的角度来理解：

// 模型上有一个顶点在局部坐标 (1, 0, 0)
// 矩阵告诉它"往哪个方向走 1 格"：
newPos = X轴向量 × 1 + Y轴向量 × 0 + Z轴向量 × 0 + 平移
       = X轴向量 × 1
       = (0.707, 0.000, 0.707)   ← 旋转后的新 X 轴方向

5. 平移为什么在单独一列里？

因为平移是"加法"，而旋转/缩放是"乘法"。它们本质上是两种不同的操作，在同一个 3×3 里无法同时表达。

// 旋转一个点 v = (x, y, z)：
v' = R · v                    ← 矩阵乘法（3×3 × 3 维 = 3 维）

// 平移一个点 v'：
v'' = v' + t                  ← 向量加法

// 如果想在一个公式里同时做旋转+平移：
// v' = R · v + t              ← 这不是矩阵乘法能直接表达的

// 所以引入齐次坐标，加一维 w=1，变成 4 维：
// | R   t |   | x |
// | 0 0 0 1 | · | y |  =  R·(x,y,z) + t·1
//                | z |     ———— 旋转部分 ————
//                | 1 |       + ——— 平移部分 ———
//
// 平移量 t 在矩阵的第 4 列，通过乘以 w=1 被"加"了进去。
一句话：平移必须放在第 4 列，是因为平移的本质是加法，而矩阵乘法的左上 3×3 只能做乘法（旋转/缩放）。 齐次坐标的 w=1 就是用来"激活"第 4 列的平移量的。
矩阵区域存储内容操作类型提取方法
m00, m10, m20（第 0 列）X 轴向量 (Xx, Xy, Xz)旋转 + 缩放——
m01, m11, m21（第 1 列）Y 轴向量 (Yx, Yy, Yz)旋转 + 缩放——
m02, m12, m22（第 2 列）Z 轴向量 (Zx, Zy, Zz)旋转 + 缩放——
m03, m13, m23（第 3 列）平移向量 (Tx, Ty, Tz)加法getTranslation()

6. 世界坐标 ↔ 相机空间

回到最初的问题。为什么 getTranslation() 提取出来的是"相机空间"坐标？

因为 Minecraft 26.2 的提交阶段，PoseStack 的原点是相机，不是世界原点（见渲染文档 §1.5）。

在 LevelRenderer.submitEntities() 内部：

// 所有实体的世界坐标在提交给渲染器之前，已被减去相机位置
this.entityRenderDispatcher.submit(state, cameraState,
        state.x - camX, state.y - camY, state.z - camZ, poseStack, output);

所以到你的渲染回调时，PoseStack 里已经累积了：

PoseStack 里的平移 = (实体世界坐标 - 相机坐标) + 骨骼动画偏移

getTranslation() 从中提取出来的就是"相对于相机的偏移"。要还原回世界坐标：

🌍 世界坐标 → 提交

Vec3 target = new Vec3(120.5, 64, -330.25);
Vec3 camera = cameraRenderState.pos;

// 因为 PoseStack 原点 = 相机
pose.translate(
    target.x - camera.x,
    target.y - camera.y,
    target.z - camera.z
);

📷 提交 → 世界坐标

Vector3f local = bonePose
    .getTranslation(new Vector3f());
Vec3 camera = info.cameraState().pos;

// 提取的是相机相对坐标，加回去
Vec3 world = new Vec3(
    camera.x + local.x,
    camera.y + local.y,
    camera.z + local.z
);
对称性：
  • 世界 → 提交：pose.translate(世界 - 相机) —— 减
  • 提交 → 世界：世界 = 相机 + local —— 加
同一对操作，方向不同，符号相反。
常见错误：
  • ❌ 忘了减 → 几何体死死跟着镜头跑
  • ❌ 减了两次 → 离世界原点越远，偏移越大
  • ❌ 直接用 entity.position() 替代矩阵提取 → 丢失了骨骼动画的偏移

7. 实战：WeaponAnchorGeoLayer 完整解读

来看你项目里真实的代码（WeaponAnchorGeoLayer.java）：

private static void capture(Player player, RenderPassInfo<?> info) {
    // 第 1 步：从 PoseStack 栈顶拍快照
    // poseStack.last() —— 回到栈顶
    // .pose()          —— 拿到 4×4 Matrix4f
    // new Matrix4f()   —— 复制一份快照
    Matrix4f bonePose = new Matrix4f(info.poseStack().last().pose());

    // 第 2 步：提取平移——从矩阵第 4 列 (m03, m13, m23) 读出
    Vector3f local = bonePose.getTranslation(new Vector3f());

    // 第 3 步：提取旋转——从左上 3×3 反算四元数
    Quaternionf rotation = bonePose.getUnnormalizedRotation(new Quaternionf());

    // 第 4 步：换算回世界坐标
    Vec3 camera = info.cameraState().pos;
    Vec3 world = new Vec3(camera.x + local.x, camera.y + local.y, camera.z + local.z);

    // 第 5 步：合理性检查——世界坐标离玩家太远就放弃
    if (world.distanceToSqr(player.position()) > SANITY_DISTANCE * SANITY_DISTANCE) {
        return;
    }
    WeaponAnchorCache.put(player,
        new Vector3f((float) world.x, (float) world.y, (float) world.z), rotation);
}
步骤做了什么JOML 层面几何意义
info.poseStack()拿到当前矩阵栈——拿到"变换历史记录本"
.last()取栈顶List<Pose> 最后一个元素只看最终结果，不关心中间步骤
.pose()拿到底层 4×4 矩阵Matrix4f 引用所有变换的最终编码
new Matrix4f(...)复制快照深拷贝矩阵防止后续操作破坏数据
getTranslation()读第 4 列取 m[12], m[13], m[14]骨骼在相机空间中的位置
getUnnormalizedRotation()从 3×3 反算四元数归一化 + 正交化 + 反三角函数骨骼在世界中的朝向

8. 自测与练习

打开上面的交互式可视化，动手验证以下结论：

  1. 单位矩阵：把所有滑块归零（旋转 0°、缩放 1.0、平移 0）。观察三根轴是否和灰色原始轴完全重合。矩阵显示是否为单位矩阵？
  2. 纯旋转：绕 Y 轴旋转 90°。红色 X 轴的三个分量变成了什么？原来的 (1,0,0) 现在变成了 (0,0,-1)——看出为什么了吗？
  3. 纯平移：只拖拽平移滑块。观察三根彩色轴的方向和长度变了吗？只有哪个数字变了？
  4. 缩放 + 平移：放大到 1.5 倍，同时平移。轴的长度变了吗？第 4 列的数字由谁决定？
  5. 回到代码：在可视化里重现 WeaponAnchorGeoLayer.capture() 的场景——骨骼经过旋转+缩放+平移后，getTranslation() 取出的就是你看到橙色箭头指向的位置。
